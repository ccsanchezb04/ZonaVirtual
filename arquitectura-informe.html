ZonaVirtual

Informe de Arquitectura — Sistema de Gestión de Pagos

ASP.NET Core 8 · Angular 17 · SQL Server · EF Core

🎯 ¿Qué hace la aplicación?

ZonaVirtual es un sistema para gestionar transacciones de pago entre usuarios y comercios. Existen dos tipos de usuarios:

PerfilIDCapacidades
Pagador perfil = 1 Ver sus propias transacciones, crear nuevas, explorar comercios
Comercio perfil = 2 Ver y filtrar transacciones recibidas, modificar las no aprobadas

🗺️ La gran imagen: Cliente ↔ Servidor ↔ Base de Datos

[ Navegador Web ]
  Angular (zona-virtual-frontend/)
        ↕ HTTP + JSON (REST API)
[ Servidor ]
  ASP.NET Core Web API (ZonaVirtual.API/)
        ↕ EF Core (ORM)
[ Base de Datos ]
  SQL Server — ZonaVirtualDB

El navegador nunca toca la base de datos directamente. Toda operación pasa por el servidor. El servidor habla con la base de datos a través de Entity Framework Core, un ORM que traduce objetos C# en tablas SQL.

🧅 Backend: 4 Capas (como una cebolla)

API ──→ Application ──→ Domain ←── Infrastructure
🟢 ZonaVirtual.Domain — El corazón del negocio
Contiene las Entidades (Usuario, Transaccion, Comercio…) y las Interfaces de repositorios. Define qué existe sin decir cómo se guarda.
Depende de: nadie — es el más puro.
🔵 ZonaVirtual.Application — Lógica de negocio
Contiene los Servicios (AuthService, ComercioService…) y los DTOs (objetos de transferencia de datos). Aquí viven las reglas: cómo registrar un usuario, validar una contraseña, aprobar una transacción.
Depende de: Domain.
🟡 ZonaVirtual.Infrastructure — Conexión real con la BD
Implementa las interfaces del Domain usando Entity Framework Core. Aquí se escribe el SQL (a través de LINQ). Si mañana cambias SQL Server por PostgreSQL, solo tocas esta capa.
Depende de: Domain.
🔴 ZonaVirtual.API — Puerta de entrada HTTP
Los Controllers reciben peticiones HTTP y devuelven JSON. Configuran la inyección de dependencias, el JWT y el middleware. El controller llama al servicio; nunca toca la base de datos directamente.
Depende de: Application.

🗂️ Entidades Clave del Dominio

// Usuario — tiene perfil 1 (Pagador) o 2 (Comercio)
public class Usuario {
    public int Id { get; set; }
    public string Nombre { get; set; }
    public int Perfil { get; set; }   // 1=Pagador, 2=Comercio
    public int? ComercioId { get; set; } // solo si es Comercio
}

// Transaccion — vincula un Pagador con un Comercio
public class Transaccion {
    public int MedioPago { get; set; }  // 32=Crédito, 29=PSE, 41=Gana, 42=Caja
    public int Estado    { get; set; }  // 1=Aprobada, 999=Pendiente, 1000/1001=Rechazada
    public decimal Total { get; set; }
    public int UsuarioId { get; set; }
    public int ComercioId { get; set; }
}
EstadoIDDescripción
Aprobada1Finalizada — no se puede modificar
Pendiente999En proceso — editable por el Comercio
Rechazada1000Rechazada — editable por el Comercio
Rechazada SR1001Rechazada sin respuesta — editable por el Comercio

🔐 Autenticación: JWT (JSON Web Token)

Al hacer login, el servidor genera un token JWT firmado que contiene la identidad del usuario. En cada petición siguiente, Angular lo adjunta automáticamente al header HTTP.

// Dentro del token (claims)
NameIdentifier → usuario.Id
Name → usuario.Identificacion
"perfil" → 1 o 2
"comercioId" → id del comercio (o vacío si es Pagador)

// El interceptor de Angular lo pega en cada llamada
Authorization: Bearer eyJhbGciOiJIUzI1NiJ9...

Las contraseñas se almacenan con PBKDF2-SHA256, 100 000 iteraciones y sal aleatoria de 16 bytes — nunca en texto plano.

⚡ Frontend Angular 17 — Rutas y Protección

/auth → Login (pública)
/pagador/mis-pagos → Solo Pagadores ← authGuard
/pagador/nuevo-pago → Solo Pagadores ← authGuard
/comercio/transacciones → Solo Comercios ← authGuard

El authGuard verifica que exista un token válido antes de mostrar la pantalla. Las rutas usan lazy loading: el código de cada sección se descarga solo cuando el usuario la visita, no todo de golpe al inicio.

🔄 Flujo Completo de una Transacción

El Pagador abre /pagador/nuevo-pago en el navegador.
Angular envía POST /api/Pagador/CrearTransaccion con el token JWT en el header.
PagadorController extrae el usuarioId del token y llama a PagadorService.
PagadorService crea el objeto Transaccion y lo pasa al repositorio.
Infrastructure guarda el registro en la tabla Transacciones de SQL Server.
El Comercio entra a /comercio/transacciones y ve la nueva transacción listada.
El Comercio puede editarla (cambiar estado, medio de pago, etc.) mientras no esté Aprobada.
